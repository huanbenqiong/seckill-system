Why · 背景与目标

从"能成交"到"会运营"

挑战一：高并发交易

  • 瞬时数万请求，绝不能超卖
  • 扣库存 / 建订单跨 Redis·MySQL，需最终一致
  • 秒杀接口需毫秒级响应、不被打垮

挑战二：运营决策

  • 系统只产出"数据"，不给"建议"
  • 查库存 / 补货 / 看大盘全靠人工 SQL
  • 能否用一句话让系统自己完成？

微服务解决"高并发安全交易"，AI Agent 解决"智能运营决策"——两层物理隔离、各自演进。

Key Tech 1 · 防超卖

Redis Lua 原子扣减

难点是读与写之间的时间窗口——数据库锁为一致性而非高吞吐设计。

  • "检查库存 + 扣减"放进同一段 Lua 脚本
  • Redis 单线程执行，天然原子、无竞态
  • 库存预热到内存，数据库不参与热路径
  • 结果：超卖率 = 0，吞吐反而更高
-- 单线程原子执行，不可被打断 local stock = redis.call('get', KEYS[1]) if tonumber(stock) > 0 then redis.call('decr', KEYS[1]) return stock - 1 -- 抢购成功 end return -1 -- 库存不足
Key Tech 2 / 3 · 异步 & 幂等

RocketMQ 削峰 + Redisson 幂等

📨

异步解耦 · RocketMQ

  • 扣减成功即发消息、立即返回
  • 订单异步创建，削峰填谷
  • 用户感知延迟 ≈ Redis 操作时间
🔒

双重幂等 · Redisson

  • 第一道：分布式锁（seckillId:userId）
  • 第二道：订单主键唯一检查
  • MQ 重复投递也绝不重复下单

分布式幂等从来不是"单一银弹"，而是"多道防线"——这是我们排查到重复订单后的核心经验。

LLM Router · 模型接入层

C# Agent LLM Router：让大模型"可切换、可靠"

独立的 ASP.NET Core 服务，作为统一的大模型网关，对接 Jan.ai 本地模型，供 Java / Python 侧调用。

  • 屏蔽底层模型差异，业务侧只调一个 /api/agent/chat
  • 运行时热切换模型，无需改代码、无需重启
  • OpenAI 兼容协议，未来可平滑接入云端模型
  • 内置容错，让 LLM 调用从"能用"升级为"可靠"
# 统一入口，业务侧无感知 POST /api/agent/chat { "messages":[…], "model":"minimax-m2.7" } # 可选 # 运行时切换默认模型 POST /api/agent/switch?model=… # 查询可用模型 / 健康检查 GET /api/agent/models GET /health

LLM Router · 韧性机制

重试 + 熔断：故障不蔓延

🔁

重试 · 指数退避

  • 针对 5xx / 429 / 连接失败等临时故障
  • 退避 1s → 2s → 4s，最多 3 次、上限 10s
  • 瞬时抖动大概率一次重试即恢复
⛔

熔断 · 状态机

  • 连续失败 5 次 → 打开熔断，快速失败
  • 休眠 30s 进入半开，试探性放行
  • 成功则恢复，失败则继续熔断

当 Jan.ai 过载时，Router 快速失败而非堆积请求——既保护调用方，也保护模型后端。还支持 API Key 认证、Request-ID 全链路追踪、RFC 7807 标准错误。

Key Points · 关键设计要点

微服务架构下的四个关键设计

🔗 服务注册与通信

Nacos 注册发现 + OpenFeign 声明式调用，服务解耦自治

🧨 高并发防超卖

goods 服务用 Redis Lua 原子脚本，秒杀零超卖

🧩 异步解耦

RocketMQ 在 goods / order 间异步削峰，最终一致

🤖 Agent 编排服务

LLM Function Calling 调度微服务 REST 接口完成运营动作

微服务把复杂系统拆成可独立演进的服务，Agent 再以标准接口把它们智能地编排起来——这正是本项目的核心设计思想。
